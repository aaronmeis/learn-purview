Comprehensive Briefing Document: Microsoft Purview Architecture, Security Controls, and Governance

Executive Summary

Organizational data environments face four primary architectural and security pressures: severe data fragmentation across multicloud and on-premises estates, an operational lack of visibility that impairs protection, rapid generative AI adoption without native guardrails, and increasingly blurred boundaries between IT, security, and data governance roles. Microsoft Purview addresses these challenges as an enterprise platform designed to govern, protect, and manage data assets regardless of their physical or logical location.

Purview divides its core operational architecture into two complementary halves: Data Security and Compliance (encompassing Information Protection, Data Loss Prevention [DLP], Insider Risk Management [IRM], Audit, eDiscovery, and Compliance Manager) and Data Governance (anchored by the Data Map and Unified Catalog). Furthermore, Purview integrates dedicated Data Security Posture Management (DSPM) for AI to address the risk of 78% of enterprise employees leveraging unmanaged, consumer-grade AI tools.

Architecturally, Purview enforces policy control across the entire lifecycle of structured, unstructured, and AI-driven data. It operates across Commercial, GCC, GCC High, and DoD cloud environments, interfacing natively with Microsoft 365 and Azure, while integrating with external clouds (AWS S3, Snowflake, Salesforce) and on-premises file repositories (SMB/NFS).

Deployments must carefully balance technical realities—such as integration runtime (IR) behavior, scanner server requirements, multicloud metadata-only extraction rules, and government-cloud feature gaps—to maintain robust compliance and data loss prevention postures.

Conceptual View

At the conceptual level, Purview delivers five top-level enterprise capabilities designed for specific operational roles:

These capabilities map directly into four core solution families: 1. Data Security: Information Protection, Data Loss Prevention, Insider Risk Management, DSPM. 2. Logical View

The logical architecture translates conceptual capabilities into vendor-neutral engines, entities, and data flows. Core logical components execute specific responsibilities:

  • Classification Engine: Scans content to detect Sensitive Information Types (SITs) and trainable classifiers.
  • Information Protection: Defines and enforces persistent sensitivity labels and encryption settings.
  • Data Loss Prevention (DLP): Monitors content activity against policies to issue alerts, user overrides, or hard blocks.
  • Insider Risk Management (IRM): Aggregates activity signals and AI interactions to identify high-risk user behavior patterns.
  • Data Map & Unified Catalog: Registers sources, manages background scanning, extracts metadata, evaluates static lineage, and exposes assets for curation and search.
  • Audit Engine: Captures system, user, administrator, and AI activity events (e.g., CopilotInteraction) into a centralized audit log.
  • DSPM for AI: Evaluates AI prompts, responses, and SharePoint grounding targets to surface oversharing risks and auto-generate protective policies.
Key Logical Flows
  1. F1 (Scan): Data Source $\rightarrow$ Data Map (extracts metadata and SIT classifications only; source content is not stored in the Data Map).
  2. F2 (On-Prem Labeling): IP Scanner $\rightarrow$ Local File Repository (evaluates content and applies persistent labels/encryption directly to files in place).
  3. F3 (DLP Evaluation): User/System Content Action $\rightarrow$ DLP Engine (evaluates SITs/labels and enforces block/audit actions).
  4. F4 (AI Audit & Insight): User AI Interaction $\rightarrow$ Unified Audit Log $\rightarrow$ DSPM Activity Explorer (emits event telemetry, prompt text, and response details where collection policies permit).

Azure Landing Zone Integration (CAF Alignment)

According to the Microsoft Cloud Adoption Framework (CAF) unified data platform reference architecture, the Microsoft Purview account should be deployed into its own dedicated Data Management Landing Zone (DMLZ) (one per Microsoft Entra ID tenant). This establishes clear ownership boundaries and tenant-wide governance.

When integrating Microsoft Fabric analytic compute within the DMLZ pattern, organizations can select from three Fabric capacity deployment models: * Option 1 (Decentralized): Mature data domains manage their own dedicated Fabric capacity within individual DMLZs, prioritizing budget autonomy over cost consolidation. * Option 2 (Centralized): A central team manages shared Fabric capacity across multiple domains, maximizing utilization for fluctuating or low-maturity workloads. * Option 3 (Hybrid): Combines shared capacity for emerging projects with defined usage thresholds to "graduate" critical data domains to dedicated capacities.

Integration Runtime (IR) Physical Matrix

Compute scanning across network boundaries relies on specialized Integration Runtimes:

  • Azure IR: Fully managed, elastic serverless compute used by default for public endpoint scanning. Automatically selects regions matching target data sources.
  • Managed Virtual Network IR: Provisions isolated compute within a Purview-managed VNet using Managed Private Endpoints.
    • Operational Rule: Automatically hibernates after 90 days of inactivity. Triggering a scan on a hibernated IR results in a status of Queued_Waking Up IR and delays execution by up to 15 minutes.
  • Self-Hosted IR (SHIR): Customer-managed VM agent requiring Java Development Kit (JDK) 11. Supports automatic background updating.
  • Kubernetes SHIR: Containerized deployment on customer Kubernetes clusters for high-throughput scaling. Requires manual version updates; auto-update is unsupported.
  • AWS IR: Elastic compute hosted by Microsoft within an AWS account to execute localized scans of S3 and RDS.

Cross-Cloud Integration Details

Amazon S3 Scanning Architecture

To scan S3 buckets, administrators create a dedicated IAM Role in AWS configured with an External ID and Microsoft Account ID provided by Purview. * Permissions: Requires AmazonS3ReadOnlyAccess or a custom policy granting s3:GetBucketLocation, s3:GetBucketPublicAccessBlock, s3:GetObject, and s3:ListBucket. * KMS Decrypt Exception: Buckets encrypted via AWS-KMS require the IAM role to be granted explicit kms:Decrypt permissions on the AWS KMS key. * SCP & Firewall Controls: AWS Service Control Policies (SCPs) must explicitly permit API calls to the target bucket region as well as us-east-1 (the AWS default API endpoint). * Limitations: S3 scanning does not support Azure Private Endpoints. AWS Glacier storage classes do not support schema extraction, classification, or sensitivity labeling.

On-Premises Information Protection Scanner Host Requirements

Deploying the scanner agent to evaluate and label SMB file shares requires an on-premises host meeting strict hardware and network prerequisites:

Hardware Sizing Minimum 4 CPU cores, 8 GB RAM, and 10 GB free disk space for temporary scanning files.

Network Endpoints HTTPS outbound (Port 443) to *.aadrm.com, *.azurerms.com, *.informationprotection.azure.com, informationprotection.hosting.portal.azure.net, *.aria.microsoft.com, and *.protection.outlook.com.

Core DSPM for AI Capabilities

  1. Overshare Risk Assessments: Purview executes an automated scan every 7 days across the top 100 SharePoint sites (by usage) to evaluate permissive user access, label coverage gaps, and sensitivity exposure referenced by Copilots and agents.
  2. Remediation Controls for Oversharing: * Restrict Site Access: Removes the entire site from Copilot and agent reasoning capabilities. * Apply Default Sensitivity Labels: Forces baseline labels on all new unlabelled content created on the site. * Restrict Access by Label: Configures explicit policies preventing agents from reasoning over content bearing specific high-value labels (e.g., "Obsidian Merger"), even if the user invoking the agent has native read permissions to the source document.
  3. Adaptive Protection Policies: Dynamically adjusts DLP restrictions based on user risk profiles calculated by Insider Risk Management: * Low-Risk Users: Permitted to process sensitive data in AI prompts, but actions generate an audit entry and user warning. * High-Risk Users: Blocked from submitting prompts or uploading files containing sensitive data into consumer AI applications (e.g., ChatGPT, DeepSeek, Google Gemini).

AI Data Logging & Telemetry Realities

  • Audit Mechanics: Interactions with M365 Copilot and Copilot Studio agents automatically generate CopilotInteraction logs within the M365 Unified Audit Log without requiring baseline configuration.
  • The Collection Policy Requirement: Prompts and responses for Copilot in Fabric, Security Copilot, and third-party LLMs are not captured in full text by default; audit logs capture event telemetry only. To retain full prompt/response text for investigation, administrators must activate an explicit Collection Policy.
  • Copilot Studio Nuance: Audit logs for Copilot Studio agents natively store only the transcript thread ID. DSPM for AI queries the backend API using this ID to retrieve and reconstruct the full chat transcript.
  • Custom AI Applications: Developers can integrate non-Microsoft AI applications into DSPM for AI using the Microsoft Graph Purview APIs and Purview SDK, binding application endpoints to a Know Your Data (KYD) policy.

Licensing Architecture Rules

  1. On-Premises Repository DLP: Licensing must be assigned to every user who adds or consumes files within a scanned share location, not merely the IP Scanner service account.
  2. Scanner Service Account: The AD service account executing the IP Scanner must hold a valid Purview license to apply sensitivity labels or encryption.
  3. Multicloud S3 Scanning: The Multicloud Scanning Connector for Amazon S3 is billed as a separate add-on to standard Purview allocations.
  4. DSPM for AI Copilot Insights: Generating specialized Copilot data risk insights requires users to hold active Microsoft 365 Copilot licenses.

Actionable Insights & Decision Rules

To ensure successful architecture, deployment, and risk management when implementing Microsoft Purview, design teams should apply the following key decision rules and mitigations:

| 2. S3 Encryption     --> Grant explicit `kms:Decrypt` to IAM Role for AWS-KMS.     |
| 3. Copilot Prompts   --> Activate explicit Collection Policy for full text logs.  |
| 4. On-Prem DLP Licensing --> License ALL end-users accessing share (Not just IR). |
| 5. Managed VNet IR   --> Account for 15-min wake-up delay after 90 days inactivity. |

Critical Operational Decision Rules

  1. Snowflake Authentication Configuration: * Rule: Authenticate Snowflake scans using RSA Key Pairs (PKCS#8). * Mitigation: Always upload the private key using the Azure CLI. Do not configure multi-line PEM keys through the Azure Portal interface, as the portal UI corrupts multi-line whitespace formatting, causing connection failures.

  2. AWS S3 KMS-Encrypted Bucket Scanning: * Rule: When target S3 buckets use custom AWS-KMS encryption, standard read access is insufficient. * Mitigation: Explicitly attach a custom policy granting kms:Decrypt on the KMS key to the AWS IAM scanner role. Ensure SCP policies allow calls to us-east-1 alongside the bucket's home region.

  3. Capturing Full Prompt/Response Telemetry for Copilots: * Rule: Do not assume standard Audit captures prompt and response text for Security Copilot or Copilot in Fabric. * Mitigation: Explicitly configure and publish a Collection Policy in Purview DSPM for AI; otherwise, investigations will yield event metadata devoid of prompt or response text.

  4. Correct Licensing of On-Premises DLP Deployments: * Rule: Licensing the IP Scanner service account alone is a compliance breach. * Mitigation: Ensure every unique human user who accesses, writes, or modifies files stored within scanned SMB/NFS UNC paths holds an appropriate Purview DLP/Information Protection license tier.

  5. Managing Hibernated Integration Runtimes: * Rule: Managed Virtual Network IRs automatically enter hibernation after 90 days of scan inactivity. * Mitigation: Account for Queued_Waking Up IR states in automated workflow pipelines, which introduce an unmitigated 15-minute execution delay while the managed VNet initializes.

  6. Updating Kubernetes Self-Hosted Integration Runtimes: * Rule: Unlike standard Windows-VM SHIR instances, Kubernetes-hosted SHIRs do not auto-update. * Mitigation: Establish an explicit operational maintenance schedule to manually pull and deploy updated container images for Kubernetes SHIR nodes.

  7. Handling S3 Scanning Gaps in Government Clouds: * Rule: The Purview Data Map in Azure Government does not support Amazon S3 or RDS connectors. * Mitigation: For government agencies requiring S3 governance, deploy a commercial Purview instance dedicated exclusively to multicloud metadata cataloging, or maintain an explicit exception in the architecture register.

  8. Overcoming Copilot Studio Audit Limits: * Rule: Audit logs for Copilot Studio store thread IDs rather than conversation text. * Mitigation: Configure eDiscovery search queries using the specific item class IPM.SkypeTeams.Message.Copilot.Studio.* to ensure full transcript review sets are compiled correctly during legal holds.
