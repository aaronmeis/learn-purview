Architectural elements are categorized across three strict abstraction altitudes based on their level of technical specificity:

2.1 Phase A: Architecture Vision

Synthesize Context & Dual-Engine Framing

Microsoft Purview addresses four primary business and operational pressures: severe data fragmentation across multicloud and on-premises environments, lack of central visibility impeding data protection and governance, accelerated adoption of generative AI tools, and blurred IT/security management boundaries [S1]. The overarching operational vision of Microsoft Purview is to provide a single, unified platform to govern, protect, and manage data wherever it lives [S1].

To realize this vision across heterogeneous enterprise boundaries, Microsoft Purview operates as a dual-engine architecture [S1, S24]: 1. Microsoft 365 Data Security & Compliance Engine: A tenant-bound, inline SaaS engine delivering real-time policy evaluation, data loss prevention (DLP), sensitivity labeling, insider risk tracking, and AI protection directly within Microsoft 365 productivity workloads and client runtimes [S1, S15, S16]. 2. Azure Data Map / Governance Engine: A subscription-deployed platform engine provisioned within an Azure Data Management Landing Zone (DMLZ). It manages out-of-band multicloud, hybrid, and SaaS metadata scanning, schema extraction, automated classification, and data cataloging [S2, S24].

Map Capabilities & Outcomes

The platform's capability baseline is defined by five foundational outcomes that form the core of TOGAF Phase A and DoDAF CV-2:

C3 Govern data Catalog, classify, lineage-map, and curate the enterprise data estate Data steward, Data source administrator [S1, S2]

Formulate Operational Vision

The operational concept establishes Microsoft Purview as a centralized governance boundary. Organizational actors and non-human agents interact with internal data workloads, while Purview extends control surfaces across non-Microsoft clouds (AWS, GCP), external SaaS platforms (Salesforce, Snowflake), on-premises file repositories, and generative AI engines (Microsoft Copilots, custom AI applications), delivering auditability and evidence directly to external regulators and internal compliance auditors [S1, S2, S16, S17, S18].

End-to-End Generative AI Data Path

The operational flow governing generative AI prompts, grounding data retrieval, real-time security enforcement, response generation, and audit logging traces through the following sequence [S16, S28]:

$$\text{User/Agent Prompt} \rightarrow \text{Grounding Data Access (SPO/ODB)} \rightarrow \text{Inline Controls (Sensitivity Labels, DLP, Access Checks)} \rightarrow \text{Model Processing} \rightarrow \text{Response Output} \rightarrow \text{Unified Audit Log } (\texttt{CopilotInteraction}) \rightarrow \text{DSPM for AI / DLM / eDiscovery}$$

  1. User/Agent Prompt: A human user or automated non-human agent submits an input prompt to an AI service (e.g., Copilot, Copilot Studio agent, custom LLM) [S16, S17].
  2. Grounding Data Access: The AI engine identifies and attempts to retrieve grounding content from M365 repositories (SharePoint Online, OneDrive for Business) [S16].
  3. Inline Control Evaluation: Purview's inline security controls evaluate user permissions, sensitivity label encryption limits, and DLP policy boundaries against the candidate grounding files [S16, S28].
  4. Model Processing: If permitted, filtered grounding context is passed to the model alongside the prompt to formulate the response [S16].
  5. Response Output: The generated response is returned to the user/agent [S16].
  6. Audit Emission: The interaction emits a CopilotInteraction record to the Unified Audit Log [S16, S21].
  7. Downstream Governance: Ingested audit telemetry triggers risk scoring in DSPM for AI, lifecycle retention evaluation in DLM, and hold indexing in eDiscovery [S15, S16, S18].

Integration APIs: Microsoft Graph Purview APIs (custom AI app prompt/response logging) [S20], Security & Compliance PowerShell (policy automation; note that app-only auth for eDiscovery cmdlets is unsupported) [S26], and Purview SDK [S20].

3. DoDAF Viewpoint Crosswalk

3.1 Operational Viewpoints (OV) & Capability Viewpoints (CV)

CV-2 (Capability Taxonomy)

The defense capability taxonomy structures Microsoft Purview into five primary capability nodes ($C1–C5$): Know Your Data ($C1$), Protect Sensitive Data ($C2$), Govern Data ($C3$), Manage Risk and Regulation ($C4$), and Secure AI Use ($C5$) [S1, S15]. These capabilities map operational mandates to underlying application engines.

OV-1 (High-Level Operational Concept)

The operational boundary of Microsoft Purview spans across enterprise organizational borders. End users and non-human AI agents interact with corporate data assets. Operating via a dual-engine model (tenant SaaS engine + Azure DMLZ Data Map), Purview sits as an authoritative inline and out-of-band monitoring and enforcement layer between enterprise users, hybrid data environments (SharePoint Online, Azure storage, AWS S3, Snowflake, Salesforce, and on-premises SMB/NFS file shares), and generative AI surfaces (Copilots and custom LLMs). It outputs structured compliance artifacts, audit records, and review sets to external regulatory authorities and internal legal bodies [S1, S2, S9, S12, S15, S16, S17, S24].

OV-2 (Operational Resource Flow)

Operational information flows sequentially across operational nodes: 1. Data Ingestion/Creation: Users/Systems place content into repositories. 2. Automated Scanning & Extraction: Scanners/Runtimes extract metadata and stream to Data Map [S9]. 3. Classification & Labeling: Classification Engine detects sensitive information; Information Protection applies sensitivity labels [S1]. 4. Inline Generative AI Path: AI prompts trigger grounding retrieval from M365, pass inline sensitivity and DLP checks, process through the model, emit responses, and write audit events [S16, S28]. 5. Policy Enforcement: DLP and DSPM engines evaluate activity against policies, executing real-time blocks or generating alerts [S14, S15]. 6. Audit Generation: Activity events and AI interaction prompts/responses emit structured records to the Unified Audit Log [S16]. 7. Investigation & Review: Analysts and Investigators process alerts and telemetry in eDiscovery and Insider Risk Management [S18, S30].

OV-5b (Operational Activity Model)

Purview executes five core operational activity streams: * Activity 1: Governance & Cataloging: Discovering assets, extracting schemas, constructing lineage [S2]. * Activity 2: Information Protection: Defining SITs, applying cryptographic protection, establishing retention schedules [S1]. * Activity 3: Data Loss Prevention: Monitoring endpoints, network streams, and cloud repositories to block exfiltration [S1, S14]. * Activity 4: AI Usage Monitoring: Tracking GenAI prompts/responses, calculating oversharing metrics, enforcing browse-to-URL policies [S15, S19]. * Activity 5: Risk & Legal Management: Aggregating user risk signals, preserving evidence via legal holds, assessing regulatory compliance scores [S1, S18, S25].

3.2 Systems Viewpoints (SV)

SV-1 (Systems Interface Description)

Purview maintains dedicated system-to-system boundaries: * First-Party Interfaces: Native API/event-stream integrations with SharePoint Online, OneDrive, Exchange Online, Microsoft Teams, and Microsoft Fabric [S5, S15, S24]. * Third-Party External Interfaces: AWS S3 (via AWS Integration Runtime), Snowflake (via Azure/SHIR IR), Salesforce (via REST API v41.0), On-Premises File Shares (via Information Protection Scanner over SMB/NFS), and OneTrust (via Microsoft Sentinel Content Hub) [S9, S10, S11, S12, S27].

SV-2 (Systems Resource Flow Description)

Physical network resource paths link system components: * Scanner to Cloud Egress: On-premises Information Protection Scanner hosts initiate outbound TLS/HTTPS connections over Port 443 to Azure/M365 cloud endpoints (*.aadrm.com, *.azurerms.com) [S13]. * Multicloud Cross-Account Link: AWS Integration Runtime hosted in a Microsoft AWS account assumes an IAM role in the customer AWS account via an External ID over secure AWS API channels [S9]. Note that Azure Private Link / Private Endpoints are unsupported when scanning Amazon S3 buckets [S9]. * Database Connector Links: SHIR and Managed VNet IR establish Private Link encrypted database sessions to Snowflake and Azure SQL endpoints [S10, S23].

SV-4 (Systems Functionality Description)

System functions map directly to software components and background processes: * Admin Portal Experience: Delivers unified policy management UI (purview.microsoft.com) [S1]. * Scanner Windows Service: Executes local file discovery, label application, and DLP enforcement on host servers [S12, S14]. * Integration Runtime Compute Instances: Executes cloud-to-cloud metadata discovery and schema extraction jobs [S3]. * Purview Browser Extension: Enforces DLP and monitoring on web-based GenAI apps within client browsers [S19, S22].

3.3 Data and Information Viewpoints (DIV)

DIV-1 (Conceptual Data Model)

The conceptual taxonomy defines core domain concepts: * Classification: Abstract identification of sensitive data types. * Sensitivity Label: Abstract metadata tag denoting organizational impact and access boundaries. * Policy: Abstract rule set mapping conditions to enforcement actions. * Data Estate: The totality of all monitored data stores across all cloud and physical locations. * AI Interaction: Abstract prompt-response exchange between an identity and a generative AI engine.

DIV-2 (Logical Data Model)

The logical data model establishes entity structural relationships: * A LABEL_POLICY publishes one or many SENSITIVITY_LABEL entities. * A SENSITIVITY_LABEL is applied to zero or many CONTENT_ITEM entities. * A SENSITIVE_INFORMATION_TYPE is detected within CONTENT_ITEM and ASSET entities. * A DATA_SOURCE contains one or many ASSET entities. * An AI_INTERACTION emits exactly one AUDIT_RECORD (e.g., CopilotInteraction) and references zero or many CONTENT_ITEM entities [S1, S2, S16, S21].

DIV-3 (Physical Data Model)

Concrete physical storage specifications: * Scanner Configuration: Stored in Microsoft SQL Server databases (2016+) hosted on host servers [S13]. * Audit Store: Unified Audit Log (UAL) physical datastores holding M365 activity records [S16]. * Scan Credentials: Cryptographically secured as secrets inside Azure Key Vault instances [S10, S11]. * Catalog Storage: Managed underlying storage within the customer's Purview Account Azure subscription [S24].

5. Architectural Gaps, Unmapped Elements, and Source Silence

Where the underlying Microsoft documentation is silent or contains explicit technical limitations, the following framework boundaries and gaps are formally recorded:

  • Air-Gapped & High-Secrecy Clouds: Microsoft documentation explicitly excludes Azure Government Secret, Azure Government Top Secret, and physically air-gapped defense networks from the supported Purview architecture scope. No mapping or feature availability claims can be made for these environments [S1, S8].

  • Third-Party Government Cloud Silence: The OneTrust integration surface is documented exclusively through partner marketplace listings [S27] and vendor marketing pages [S31]. There is zero Microsoft source documentation addressing whether the OneTrust connector functions within Office 365 GCC, GCC High, or DoD environments. Vendor claims regarding bidirectional sensitivity label synchronization remain classified as UNVERIFIED [S27, S31].

  • AWS S3 & Multicloud Technical Limitations:

  • Storage Class Limitations: Amazon S3 Glacier storage classes do not support schema extraction, classification, or sensitivity labeling [S9].
  • Private Endpoint Constraints: Azure Private Link / Private Endpoints are unsupported when scanning Amazon S3 buckets [S9].
  • Encryption Permissions: Scanning KMS-encrypted S3 buckets fails unless explicit kms:Decrypt policy permissions are attached to the assumed IAM role [S9].

  • Azure Government Exclusion: The Amazon S3 Multicloud Scanning Connector is explicitly unsupported in Azure Government Data Map instances [S4].

  • AI Telemetry & Payload Retrieval Gaps:

  • Copilot Studio Payload Omission: Standard M365 Unified Audit Log records store only the transcript thread ID for Copilot Studio interactions [S21]. Full chat prompt and response text retrieval requires active ingestion via DSPM for AI or an enforced Collection Policy [S15, S21].

  • Collection Policy Requirements: Copilot in Fabric, Security Copilot, and custom non-Copilot AI applications emit standard audit events but omit prompt/response text payloads unless an active Collection Policy is configured [S15].

  • Licensing Enforcement Constraints:

  • On-Premises DLP Licensing: Every user who accesses or creates files within a scanned on-premises repository requires a Purview DLP license—licensing only the scanner service account is non-compliant [S14].
  • Scanner Account Licensing: The Information Protection Scanner service account itself must hold an active Purview license to apply classifications or labels [S13].

  • DSPM for AI Insights: Generating Copilot usage risk analytics requires underlying Microsoft 365 Copilot licenses for target users [S19].

  • Portal Management Deficiencies:

  • Snowflake Key Formatting Corruption: Pasting multi-line RSA private keys into the Azure Purview portal web interface corrupts PEM formatting. Configure Snowflake key-pair authentication exclusively via Azure CLI or Azure Key Vault secret injection [S10].

  • Regional / Feature Exclusions:

  • DSPM for AI Operational Restrictions: In GCC High and DoD clouds, browse-to-URL blocking policies cannot be created, and monitoring is constrained strictly to a pre-defined list of supported AI sites [S7].

  • Lineage Exclusions: Synapse pipeline lineage and preview data sources are explicitly unsupported in Azure Government Data Map instances [S4].

  • PowerShell Cmdlet Limitations: Automated management scripts utilizing the Security & Compliance PowerShell module do not support app-only authentication for eDiscovery cmdlets. Administrators must migrate automation workloads to Microsoft Graph APIs [S26].

  • Documentation Discrepancies: A direct conflict exists within official Microsoft service descriptions regarding the compliance baseline of Office 365 GCC:

  • Reference [S5] (Plan for Microsoft Purview - GCC deployments) states that GCC meets FedRAMP Moderate.
  • Reference [S8] (Cloud feature availability for US Government customers) states that GCC meets FedRAMP High. Architects must resolve this discrepancy directly against the FedRAMP Marketplace registry prior to submitting system authorization artifacts.
