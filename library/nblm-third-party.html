2. Technical Deep Dive into Documented External Integrations

2.1 Multicloud Storage Integration: Amazon S3 (AWS)

Architecture & Execution

Microsoft Purview executes scanning across Amazon S3 by deploying and hosting an AWS Integration Runtime (IR) within a Microsoft-owned AWS account. The connector connects securely to customer AWS S3 buckets to inspect unstructured data, returning only metadata and classification findings back to the Azure tenant. File content is read strictly during the scan execution and is never stored or transferred back to Microsoft Purview.

Prerequisites & IAM Setup

  • Role ARN Setup: A dedicated AWS IAM role must be created specifically for Purview.
  • Trust Relationship: The IAM role trust policy must mandate a specific Microsoft Account ID (e.g., 181328463391) and a tenant-unique External ID provided in the Purview portal under credentials setup.
  • IAM Permissions: The role must be granted either the AWS-managed policy AmazonS3ReadOnlyAccess or a custom JSON policy containing explicit minimum required actions:
  • s3:GetBucketLocation
  • s3:GetBucketPublicAccessBlock
  • s3:GetObject
  • s3:ListBucket (or s3:ListAllMyBuckets when scanning an entire AWS account)
  • KMS Decryption: For buckets encrypted using AWS Key Management Service (AWS-KMS), a custom IAM policy granting the kms:Decrypt action on the relevant KMS key resources must be explicitly attached to the scanning role.
  • Bucket & Service Control Policies (SCPs): AWS Service Control Policies and bucket policies must explicitly allow API calls (AssumeRole, GetBucketLocation, GetObject, ListBucket, GetBucketPublicAccessBlock) and must not block access to region us-east-1 (the default AWS region used for initial API endpoint calls).

Regional Scanning Mapping

To manage data transit fees, regional sovereignty, and latency, Microsoft Purview processes S3 bucket scans using regional scanning engines mapped 1:1 to the underlying AWS storage location:

Technical Constraints

  • Purview registered sources support root bucket URLs only (e.g., s3://bucketname). Sub-folder scoping is configured during scan rule definition, not during source registration.
  • Scanning Amazon S3 assets via Microsoft Purview private endpoints is unsupported.
  • AWS Glacier storage classes do not support schema extraction, content classification, or sensitivity labels.
  • The Multicloud Scanning Connector is explicitly unsupported in Azure Government deployments.

2.2 SaaS & Cloud Database Integrations: Snowflake and Salesforce

Snowflake Integration Specifications

  • Supported Runtimes: Connects via Azure IR, Managed VNet IR v2, or Self-Hosted Integration Runtime (SHIR). Any virtual machine hosting a SHIR node requires the Java Development Kit (JDK 11) installed as a strict operational dependency.
  • Extracted Data: Ingests technical metadata, schema structure, sensitive data classification, and static data lineage into the Data Map and Catalog.
  • Authentication: Supports Key Pair authentication using a PKCS#8 RSA key pair. Basic username/password authentication is officially scheduled for retirement by Snowflake in 2026.
  • Key Storage Requirement: When configuring RSA private keys, administrators must import multi-line PEM key strings using the Azure CLI. Inputting multi-line PEM private keys via the Azure Portal UI corrupts the string formatting.
  • Catalog Maintenance: Objects deleted at the Snowflake source do not automatically purge from the Purview Data Map; manual catalog cleanup commands must be executed periodically.

Salesforce Integration Specifications

  • Supported Runtimes & Protocol: Ingests metadata over Salesforce REST API v41.0 utilizing either Azure IR or Managed VNet IR v2 / SHIR (SHIR nodes require JDK 11).
  • Authentication: Utilizes a Salesforce OAuth Connected App consumer key combined with a user password held in an Azure Key Vault secret referenced by Purview credentials.
  • Capabilities & Limitations: Extracts organizational objects, fields, and high-level technical metadata only. Salesforce connectors provided by Microsoft Purview offer zero content classification or sensitivity labeling capabilities. Deleted objects linger in the catalog requiring manual purging.

2.3 On-Premises Repositories: SMB/NFS File Shares and SharePoint Server

Scanner Architecture

The Microsoft Purview Information Protection Scanner operates as a Windows service hosted within the customer's on-premises network or IaaS virtual machine. It uses SMB (with NFS support in preview) over UNC paths to scan file shares, and integrates natively with on-premises SharePoint Server (2013, 2016, and 2019).

The scanner discovers, indexes, classifies, labels, and applies RMS encryption to files in place while enforcing on-premises Data Loss Prevention (DLP) policies. State configuration, policy cache, and operational metadata are persisted in a local or remote Microsoft SQL Server instance.

System & Host Prerequisites

  • Host OS: Dedicated physical or virtual machine running 64-bit Windows Server 2016, 2019, 2022, or 2025 (Server Core and Nano Server are strictly unsupported).
  • Runtime & Hardware Sizing: Minimum 4 CPU cores and 8 GB RAM, plus at least 10 GB of available disk space for temporary file extraction. SHIR co-deployments require JDK 11.
  • Database: Microsoft SQL Server 2016 or higher (any edition) configured with a case-insensitive collation.
  • Service Account: An Active Directory service account synchronized with Microsoft Entra ID. Requires Read, Write, and Modify permissions on target shares/sites for enforcing protection (Read-only for discovery-mode scans).
  • Network Egress: Outbound HTTPS (Port 443) connectivity to specific Microsoft endpoints: *.aadrm.com, *.azurerms.com, *.informationprotection.azure.com, informationprotection.hosting.portal.azure.net, *.aria.microsoft.com, and *.protection.outlook.com.

Licensing Rules

  • Every individual user who creates, modifies, or consumes files within an on-premises scanned share or SharePoint site requires an appropriate Purview Information Protection license.
  • The scanner service account itself must be actively licensed to apply classifications, labels, or encryption policies.

2.4 Governance, DSPM, and Partner Tools: OneTrust and GenAI Ecosystem

OneTrust Integration

Ingestion into Purview Data Security Posture Management (DSPM) occurs via partner applications deployed through the Microsoft Sentinel Content Hub. Sensitive data findings discovered by OneTrust scans are pushed into Purview DSPM to enrich cross-estate data visibility.

Source Verification Note: While partner documentation (S31) claims two-way sensitivity label synchronization between OneTrust and Purview Information Protection, official Microsoft Learn documentation (S27) treats this integration path as a preview capability without verifying far-side label writeback.

Consumer & Non-Managed GenAI Control

DSPM for AI enforces discovery and exfiltration guardrails across consumer GenAI platforms (including ChatGPT Consumer, DeepSeek, and Google Gemini). Coverage relies on endpoint monitoring deployed via Purview-onboarded Windows/Mac devices and the Microsoft Edge browser extension, capturing local app network traffic and web sessions.

Adaptive Protection Policies: Dynamically enforce response actions based on user risk profiles. Minor-risk user prompts are logged for audit analysis, while high-risk users are automatically blocked from pasting or uploading sensitive information types (SITs) into unmanaged AI prompts.

Enterprise GenAI App APIs, SDKs, and Logging Boundaries

Custom enterprise AI applications integrate using the Purview SDK and Microsoft Graph Purview APIs. Organizations establish Microsoft Purview "Know Your Data" (KYD) policies to capture user prompts, generated responses, and context metadata into Purview DSPM and the Unified Audit Log.

  • Critical Architectural Logging Distinction for Copilots:*
  • Copilot in Fabric & Security Copilot: Prompts and responses are not captured by default. Purview logs non-content audit metadata only unless an explicit Collection Policy is configured in Purview to capture the raw prompt and response text.
  • Copilot Studio Agents: The standard M365 Unified Audit Log (CopilotInteraction) records only the transcript thread ID. Full chat transcript text retrieval requires enabling DSPM for AI.

Architectural Risk Note: Identity Boundary Decay & Oversharing

Unmonitored agent deployment introduces severe identity boundary decay. DSPM for AI agent reports highlight high-risk configurations, such as top agents open to internet users that allow interactions by unauthenticated or anonymous users. When these agents are grounded on enterprise data sources (e.g., SharePoint Online sites with overly permissive read access), sensitive data is exposed to external actors. Mitigation requires enforcing site-level access restrictions or setting "Restrict Access by Label" policies so agents cannot reason over classified content.

3. Mentioned But Undocumented / Partially Documented External Integrations

Architectural Governance Topology (CAF Mandate)

According to the Microsoft Cloud Adoption Framework (CAF) unified data platform architecture (S24), Microsoft Purview must be deployed into a dedicated Data Management Landing Zone (DMLZ) subscription. CAF mandates a strict topology limit of one Purview account per Microsoft Entra ID tenant to preserve tenant-wide governance control and avoid fragmented policy enforcement.

Non-Microsoft Cloud Databases & Warehouses

  • Amazon RDS & Amazon Redshift: Listed in Purview documentation as supported scanning targets via Azure IR, AWS IR, or Kubernetes SHIR (requires JDK 11). Explicit step-by-step connection procedures, authentication configurations, and schema extraction specs are omitted from source docs.
  • Google BigQuery: Documented as a supported scanning target via Self-Hosted IR (SHIR) and Kubernetes SHIR (requires JDK 11). Authentication workflows, service account requirements, and permission scopes remain undocumented.
  • Oracle, SAP HANA, SAP BW, Db2, Cassandra, MongoDB, MySQL, PostgreSQL, Teradata: Listed in the Data Map Integration Runtime matrix as supported via SHIR, Kubernetes SHIR, or Managed VNet IR v2. Detailed connector setup, network firewall requirements, and extracted asset specifications are omitted.

Enterprise ERP Systems (SAP & Oracle)

  • SAP ECC, SAP S/4HANA, & Oracle Database: Highlighted in CAF reference architectures (S24) as integrating into OneLake via Fabric Mirroring to replicate transactional data in near real time for analytical ingestion. While Fabric mirroring mechanics are documented, their direct Purview Data Map technical scanning parameters, metadata extraction schemas, and credential setup remain undocumented in Purview Learn docs.

On-Premises & Arc Databases

  • SQL Server (On-Premises & Azure-Arc Enabled) & HDFS: Documented in the IR matrix as requiring SHIR or Kubernetes SHIR deployment (requires JDK 11). Specific data entities exchanged, authentication configurations, and classification parameters are undocumented.

Third-Party SaaS Apps & Business Intelligence Tools

  • Looker, Qlik Sense, Tableau, Dataverse, Erwin: Listed in the Data Map IR matrix as supported scanning targets (via Azure IR, Managed VNet IR v2, or SHIR). Specific technical setup parameters, API requirements, and permissions are omitted.

Non-Microsoft AI Agents

  • Third-Party AI Agents (e.g., ChatGPT Enterprise & Claude Enterprise Agents): Microsoft Learn documentation (S17) explicitly notes that third-party agents, such as ChatGPT Enterprise or Claude Enterprise agents, are unsupported under Purview AI agent data protection features.

4. Silence and Gap Analysis Register

Integration Domain / Capability Documented Silence / Source Gap Architectural Risk Note
ITSM & Ticketing Systems (e.g., ServiceNow, Jira) Sources are completely silent regarding direct ITSM or ticketing platform integration. No native mechanisms exist in the source context for automated ticket creation, incident response workflow syncs, or bi-directional status updates. Security teams must manually bridge compliance alerts to operational ticketing systems, increasing Mean Time to Respond (MTTR) and risk of unaddressed DLP incidents.
Third-Party SIEM & SOAR Systems (Non-Microsoft) While Microsoft Sentinel is documented as the ingestion vector for OneTrust partner data, sources are completely silent on native event export streams, syslog feeds, or direct integrations with non-Microsoft SIEM/SOAR platforms (e.g., Splunk, Datadog). Multi-vendor SOC environments face operational visibility silos, requiring custom Graph API scripting to extract Unified Audit Log events into third-party SIEMs.
Third-Party Identity Providers (IdPs) Sources thoroughly document Microsoft Entra ID and Active Directory synchronization, but remain completely silent regarding direct federation or identity attribute mapping with non-Microsoft IdPs (e.g., Okta, Ping Identity). Access governance and Conditional Access evaluations in Purview rely entirely on Entra ID objects, creating identity boundary gaps if non-Microsoft IdPs are not synced to Entra ID.
Government-Cloud Support for Partner Solutions No Microsoft documentation confirms government-cloud (GCC, GCC High, DoD) availability for third-party partner integrations (e.g., OneTrust) or third-party AI site monitoring. Federal agencies cannot assume partner integrations or AI site monitoring capabilities operate within FedRAMP or IL4/IL5 boundaries without explicit tenant-level verification.
Air-Gapped & Secret Clouds Sources explicitly declare that no Secret, Top Secret, or air-gapped cloud support exists or is documented within the scope of Microsoft Purview capabilities. National security workloads operating in disconnected or air-gapped environments cannot utilize cloud-hosted Purview services for data governance or DLP.
Federal Compliance Discrepancy Official Microsoft documentation contains an unresolved conflict: M365 GCC service descriptions (S5) state that GCC meets FedRAMP Moderate, whereas Azure Security documentation (S8) states that GCC meets FedRAMP High. Compliance officers must independently verify current authorization boundaries against the official FedRAMP Marketplace listing prior to ATO submission.
