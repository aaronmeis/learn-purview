Logical Architecture View: Microsoft Purview

1. Architecture Scope & Conceptual Boundaries

Microsoft Purview is an enterprise information governance and data security platform designed to govern, protect, and manage organizational data across its entire lifecycle within heterogeneous data estates. Its logical architecture provides systemic visibility, control, and compliance enforcing across four operational domains: data fragmentation across multi-cloud and on-premises repositories, unmonitored exposure of sensitive information, rapid adoption of Generative AI applications and autonomous agents, and overlapping administrative boundaries across IT, security, and risk teams.

From a vendor-neutral architectural altitude, Microsoft Purview establishes functional boundaries separating four core operational domains: * Data Security: Establishes sensitive data recognition, persistent access control and encryption labeling, real-time data loss prevention (DLP) across endpoints, networks, and cloud services, and user risk signal aggregation. * Data Governance: Orchestrates source registration, technical metadata extraction, data cataloging, schema discovery, and static/dynamic lineage mapping across enterprise repositories. * Data Compliance: Executes activity audit logging, legal hold enforcement, evidentiary discovery, retention/lifecycle rules, and regulatory baseline assessments. * AI Protections: Manages real-time prompt/response telemetry, AI application and agent discovery, oversharing risk assessment, and policy enforcement across generative AI models and intelligent agents.

Core Architectural Principles

  1. Metadata-Only Extraction for External Estate: Scanners inspecting multi-cloud repositories (e.g., AWS S3) or third-party data platforms extract technical metadata, schema attributes, and classification tags only. Raw source content is scanned strictly in-place within localized execution buffers and is never ingested or stored within the central governance boundary.
  2. In-Place Data Control: Protection mechanisms—including rights-management encryption, visual markings, lifecycle retention triggers, and access restrictions—are applied in-place directly within native storage repositories or localized endpoint environments.
  3. Default Ingestion of Activity Telemetry: Interaction telemetry, system events, and prompt/response metadata generated by supported generative AI models and enterprise services are automatically routed into the centralized audit and compliance data path without requiring manual agent deployment.
  4. Logical Control Plane and Data Plane Decoupling: Administrative policies, classification rules, and compliance frameworks are orchestrated centrally within the Control Plane. Enforcement and pattern matching occur strictly within local Data/Execution Planes (such as endpoint memory buffers, network edge interceptors, or native repository runtimes) to eliminate unnecessary content egress over the wire.

SILENCE / UNVERIFIED: Edge DLP Latency & Offline Guarantees - The source context is silent regarding explicit logical boundary definitions for Secret or Top Secret cloud environments, air-gapped network architectures, or guaranteed SLA latencies for edge Data Loss Prevention (DLP) evaluation when endpoints operate in disconnected or degraded network states.

Nuanced Component Behaviors

  • DSPM for AI Assessment Engine: Performs automated, recurring background scans (every 7 days) across top storage locations (such as the top 100 First-Party Content Repositories / SharePoint Online sites by usage) to identify overly permissive user access, missing sensitivity labels, and potential AI oversharing vectors.
  • Audit Engine & Copilot Interactions: Standard Copilot interactions log user prompts, generated outputs, and referenced file pointers directly to the audit engine. For specialized agent frameworks (such as Copilot Studio), the Audit Engine records only the transcript thread ID, relying on DSPM for AI to query underlying conversational stores when full textual inspection is required.
  • eDiscovery Target Mechanics for AI: Copilot interactions do not reside in a single monolithic database. Instead, they are persisted as discrete, MAPI-indexed conversation items within underlying user Exchange and chat stores. The eDiscovery Engine targets these interactions using specific item class filtering (e.g., IPM.SkypeTeams.Message.Copilot.Studio.*), enabling legal sweeps to isolate agent dialogue streams without retrieving unrelated user mailbox items.
  • Explicit Collection Policies: Prompt and response text for specific workloads—such as Copilot in Fabric and Security Copilot—are omitted from default audit payload streams. Capturing full prompt/response text for these workloads requires configuring an explicit Collection Policy; without it, only basic execution metadata is logged.
  • Adaptive DLP Policy Execution: The DLP Engine dynamically modulates enforcement actions based on real-time user risk scores supplied by Insider Risk Management. For identical file access actions, high-risk users are actively blocked from pasting sensitive content into consumer AI web applications, whereas low-risk users receive an informational banner while their action is logged.

Explicit Entity Definitions

  • Sensitivity Label: A persistent metadata tag defined by administrators that encapsulates operational controls, including access control lists, visual header/footer markings, and rights-management encryption rules.
  • Sensitive Information Type (SIT): A pattern-matching logic pattern or machine-learning model used by the Classification Engine to recognize confidential data elements (e.g., credit card numbers, national identification patterns, or custom source code templates).
  • Policy: An administrative rule container defining targeted location scopes, triggering conditions, user risk thresholds, and enforcement actions across security, compliance, retention, and governance domains.
  • Data Source: A registered target repository, database system, cloud storage service, or file server hosting raw enterprise data.
  • Asset: A discrete logical entity representation (e.g., database table, file, schema, or report) discovered within a Data Source.
  • Audit Record: An immutable, time-stamped log entry generated by user, administrative, or agent interactions across supported cloud and enterprise workloads.
  • AI Interaction: A structured data bundle capturing dialogue context (prompts, generated outputs, agent identifiers, and referenced file pointers) between a user/agent and a generative AI application.
  • Case: An investigative workspace utilized to aggregate relevant evidence, apply location-based legal holds, execute review workflows, and export evidentiary packages.

4. Logical Data Flows and Interaction Patterns

Operational capabilities are executed through six primary logical data flows across central engines, edge interceptors, and external storage repositories.

F2 On-Premises Labeling & Protection Information Protection Scanner On-Premises File Repository In-place label metadata modification and rights-management encryption application Scheduled Scan Job / Asynchronous

Sequential Execution Details

F1: Metadata Scanning

  1. The Data Map initiates a scheduled or manual scan job against a registered Data Source.
  2. The runtime engine establishes an authenticated connection to inspect object schemas and storage structural attributes.
  3. The embedded Classification Engine processes transient object streams locally within volatile memory buffers to detect matching SITs.
  4. Extracted technical attributes, schema layouts, and classification identifiers are sent to the Data Map. Raw content streams are purged from memory buffers immediately after inspection.
  5. The Data Map updates Asset entity definitions and constructs derived lineage graphs.

F2: On-Premises Labeling & Protection

  1. The scanning service iterates through targeted file share UNC paths via SMB or NFS (preview) protocols.
  2. Files are read locally into memory buffers and evaluated against published Information Protection rules.
  3. If rule criteria are met, the scanner writes sensitivity label metadata directly into the file header in-place.
  4. If rights-management encryption is required, the scanner applies cryptographic protection in-place using configured service account credentials.

F3: DLP Policy Evaluation

  1. A user or agent initiates an operation on a file or text buffer (e.g., copying text, uploading a document, or entering text into a web form).
  2. The endpoint or workload interceptor isolates a transient memory buffer snippet and context metadata, avoiding the transmission of full multi-gigabyte files across the network.
  3. The DLP Engine evaluates the payload against active Policies matching the user's risk context, target destination, and embedded SITs / Sensitivity Labels.
  4. Execution Decision: * Allowed / Audited: Action completes locally; an activity event is asynchronously dispatched to the Audit Engine. * Blocked: Action is intercepted at the local interface; a user notification banner is presented, and an intercept event is queued for administrative alerting.

F4: AI Interaction Auditing

  1. A user or autonomous agent submits a prompt to a generative AI application or agent interface.
  2. The application framework constructs an interaction event payload containing prompt text, generated output text, application/agent ID, and pointers to referenced files.
  3. The event payload is dispatched asynchronously to the Unified Audit Log, writing a CopilotInteraction record.

F5: AI Security & Oversharing Analysis

  1. The DSPM for AI engine ingests CopilotInteraction telemetry streams from the Unified Audit Log.
  2. Concurrently, weekly background assessment jobs analyze storage repository access control lists (e.g., evaluating permissions across the top 100 SharePoint sites by usage to identify overly permissive access settings).
  3. Telemetry is aggregated to construct risk analytics, identifying high-risk user prompt patterns, unauthenticated agent interactions, and unprotected sensitive files.
  4. Administrative dashboards are updated with recommended one-click security policies (e.g., restricting site access by label).

F6: Compliance Retention & Discovery Collection

  1. Legal personnel create an eDiscovery Case or define a retention rule targeting AI workload locations.
  2. The eDiscovery Engine queries underlying storage stores using targeted item class filtering (e.g., IPM.SkypeTeams.Message.Copilot.Studio.* within Exchange/chat MAPI stores).
  3. Matching conversation threads, prompt/response pairs, and associated grounding files are placed on location hold and copied into an eDiscovery review set for evidentiary analysis.

Sequential AI Data Path Stages

1. Prompt Submission

A user or autonomous agent initiates an interaction by submitting a textual or multi-modal prompt to an AI model or specialized agent interface.

2. Grounding Data Retrieval

The AI application framework attempts to retrieve enterprise context (grounding data) from native repositories (e.g., First-Party Content Repositories / SharePoint Online, OneDrive, or database endpoints) to supply contextual data to the model.

3. Policy Control Evaluation (Logical Governance Gate)

Before candidate grounding data is passed to the model, the logical architecture enforces a multi-layered policy evaluation gate: * Access Verification: Validates that the initiating user or agent identity possesses explicit read permissions for candidate grounding documents. * Sensitivity Label Restrictions: Evaluates whether Sensitivity Labels applied to grounding items prohibit AI processing (e.g., policies restricting Copilot from reasoning over highly confidential acquisition documents). * DLP & Exfiltration Checks: Scans prompt text and candidate grounding data for restricted SITs targeted by exfiltration rules. * Gate Decision: If protection policies restrict access to candidate documents, those specific items are stripped from the grounding context. If all candidate grounding items are restricted, model execution halts, returning a system notification indicating protection enforcement.

4. Model Processing & Response Generation

The AI model processes the filtered grounding context and prompt, generating a response constrained strictly to authorized organizational context.

5. Audit & Activity Logging

  • The system asynchronously emits a CopilotInteraction record to the Unified Audit Log, capturing prompt text, generated response, referenced file identifiers, applied sensitivity labels, and agent identity metadata.
  • Log records are immediately available to DSPM for AI risk analytics, Insider Risk Management triage, Communication Compliance, and eDiscovery collection.

AI Overshare Mitigation Mechanisms

To prevent broad organizational exposure resulting from overly permissive access permissions combined with AI search interfaces, the logical architecture provides three primary mitigation mechanisms via DSPM for AI:

  • Restricting Site Access by Label: Administrators can deploy policies restricting AI models and agents from reasoning over entire sites or specific document sets tagged with sensitive labels, regardless of individual user access rights.
  • Default Sensitivity Labeling: Enforces automatic default baseline labeling on newly ingested or created items within high-usage SharePoint sites, ensuring missing classifications do not expose raw content to AI indexing.
  • Total Site Removal / Isolation: Provides a one-click isolation command within DSPM for AI that completely removes an overly permissive site from the search and reasoning index of Copilots and agents without altering underlying user permissions.

Logical AI Nuances

  • Agent Identity Tracking: Non-human autonomous agents created via Copilot Studio or Microsoft Foundry inherit governance boundaries from parent workloads but are tracked explicitly via Enterprise Identity Provider / Microsoft Entra Agent IDs. This enables security systems to audit and govern non-human data access identically to human user identities.
  • Third-Party & Web AI Isolation: Interactions with unmanaged third-party AI web applications (e.g., consumer ChatGPT or DeepSeek) are monitored at the endpoint/network layer via device onboarding and browser extensions. Adaptive protection rules automatically block high-risk users from entering sensitive data into non-enterprise prompts while permitting low-risk users under audited conditions.
  • Transcript Retrieval Divergence: Copilot Studio logs transcript thread IDs to the central Audit log. When detailed textual inspection is required for compliance investigations, DSPM for AI utilizes targeted APIs to resolve and retrieve full conversational transcripts.

6. Vendor-Neutral Nuances, Constraints, and Silence Register

Architectural Constraints Supported by Source Data

  1. Zero Raw Content Ingress for Multicloud Scans: Multicloud Data Map scanning architectures operate under a strict non-ingestion principle. When scanning AWS S3 or Snowflake, the compute runtime inspects content streams in-memory to derive metadata and classification tags. Raw content is never transmitted across the management boundary into the governance storage platform.
  2. Agent Protection Inheritance: Non-human agents built via Copilot Studio or Microsoft Foundry do not maintain independent security silos; they inherit classification rules, DLP constraints, and retention policies directly from their parent operational tenant and underlying data endpoints.
  3. Mandatory Collection Policies for Specific Copilot Workloads: Prompt and response text for specific enterprise AI workloads (e.g., Copilot in Fabric and Security Copilot) are explicitly omitted from default audit streams unless an administrative Collection Policy is active.
  4. AWS S3 Azure Government Exclusion: While the Multicloud Scanning Connector supports Amazon S3 metadata extraction in commercial accounts, scanning Amazon S3 data sources is explicitly excluded and unsupported in Azure Government environments.
