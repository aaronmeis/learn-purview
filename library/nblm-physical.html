2. On-Premises and Hybrid Infrastructure Deployment

2.1 Information Protection & DLP Scanner Requirements

The deployment of the Information Protection Scanner for discovering, classifying, labeling, and enforcing DLP on on-premises file repositories (SMB file shares and preview NFS) requires adherence to the following hardware, software, network, and identity specifications:

  • Operating System: 64-bit Windows Server 2016, 2019, 2022, or 2025. Forbidden configurations: Windows Server Core and Windows Server Nano are explicitly unsupported.
  • Hardware Sizing: Minimum allocation of 4 CPU cores, 8 GB RAM, and at least 10 GB of available disk space for temporary scanning files.
  • Database Infrastructure: SQL Server 2016 or later (local or remote instance) configured with a case-insensitive collation to store scanner configuration data.
  • Identity & Active Directory Rights: Dedicated Active Directory service account synchronized to Microsoft Entra ID. The account must possess Read, Write, and Modify permissions on target file shares for enforcement mode, or Read-only access for discovery/inventory mode.
  • Licensing Prerequisites:
    • Scanner Account: The dedicated Active Directory service account driving the scanner must be assigned an active Microsoft 365 license containing Information Protection capabilities to perform classification, labeling, and protection tasks.
    • Repository Users: DLP enforcement across on-premises file shares requires every user who creates, adds, or consumes files in scanned locations to hold an appropriate Microsoft 365 DLP license.
  • Network Egress Endpoints: Unrestricted outbound HTTPS (TCP port 443) connectivity from the host to:
    • *.aadrm.com
    • *.azurerms.com
    • *.informationprotection.azure.com
    • informationprotection.hosting.portal.azure.net
    • *.aria.microsoft.com
    • *.protection.outlook.com
  • Software Client: Requires installation of the full Information Protection client (the standalone PowerShell module alone is insufficient).

Managed Virtual Network IR Hibernation Rules

If a Managed Virtual Network IR experiences 90 consecutive days of inactivity (no scan executions), it automatically enters a Hibernated state: 1. Test Connection Behavior: Executing a "Test Connection" on a hibernated IR fails immediately and raises an error requesting a retry after 15 minutes while the VNet provisions back to an active state. 2. Scan Execution Behavior: Direct scan invocations (Run scan now, scheduled triggers, or API calls) against a hibernated IR display the execution status Queued_Waking Up IR (instead of standard Queued) and incur up to 15 additional minutes of latency while the compute environment unhibernates. Subsequent scans execute normally.

3. Data Stores, Secrets, and Data Residency

  • Secret & Credential Mechanics Disambiguation:
    • Key Vault Secrets: Used strictly for storing string credentials and private key payloads (e.g., Snowflake RSA private keys, Salesforce user passwords). Purview references these via Key Vault Secret URIs within its credential objects.
    • Native AWS Cross-Account Trust: AWS IAM Role ARN authentication does not store a secret string in Azure Key Vault. Instead, Purview authenticates directly via cross-account trust using Microsoft's AWS Account ID and a unique Purview-generated External ID configured directly within the Purview Credential object.
  • Multicloud Data Residency Controls: Connector architecture enforces strict boundary protection for external cloud data stores (such as Amazon S3, Snowflake, and Salesforce). Scanning runtimes extract metadata, schemas, and classifications only. Raw source content is inspected in-memory during scanning and is never written or permanently stored back to Azure Purview data stores.
  • Unified Audit Log & AI Telemetry Storage:
    • Standard workload telemetry and AI prompts/responses emit structured CopilotInteraction audit records directly to the Microsoft 365 Unified Audit Log.
    • Collection Policy Exception & Operations Risk: For Copilot in Fabric and Microsoft Security Copilot, prompt and response text are not captured by default; only basic activity metadata is logged unless an explicit Collection Policy is established in Purview. Operational Risk: Without an active Collection Policy, security operations and eDiscovery teams will have zero visibility into prompt payload text during compliance investigations.
    • Copilot Studio Mechanics: Copilot Studio records store only the transcript thread ID within the standard Audit log solution; the actual chat transcript content is retrieved separately by the DSPM for AI layer.
    • eDiscovery & Lifecycle: AI interaction records flow from the Unified Audit Log into Data Lifecycle Management under the location "Microsoft Copilot Experiences" and are discoverable via eDiscovery using specific ItemClass identifiers (e.g., IPM.SkypeTeams.Message.Copilot.Studio.*).
  • DSPM for AI Remediation & Control Actions:
    • Adaptive Protection: Dynamically modulates enforcement based on user risk tiers (high, medium, low). High-risk users are explicitly blocked from entering or uploading sensitive data into unmanaged consumer LLM tools (e.g., ChatGPT consumer, DeepSeek, Google Gemini), while low-risk users are permitted with an audit event recorded.
    • Restrict Access by Label: A site-level and item-level remediation policy within DSPM for AI. Blocks Copilots and AI agents from reasoning over content marked with designated sensitivity labels (e.g., highly confidential M&A documents), even if the user invoking the agent possesses underlying site read permissions. Alternatively, admins can restrict the entire site from Copilot and agent indexing.

Operational Traps & Integration Risk Controls
  1. Snowflake RSA Key Deployment Trap: Multi-line PEM RSA private keys used for Snowflake authentication become corrupted when entered or saved through the Azure Portal UI. Configurations must be deployed exclusively via the Azure CLI (az purview credential create/update) to preserve PEM string formatting.
  2. AWS Service Control Policy (SCP) & Region Boundary: S3 scanning requires an AWS IAM policy with read permissions and KMS Decrypt. Furthermore, AWS SCPs must explicitly permit unblocked API calls (AssumeRole, GetBucketLocation, GetObject, ListBucket, GetBucketPublicAccessBlock) to the us-east-1 region (the default global AWS endpoint for role assumption) regardless of the host bucket's geographic region.

6. Licensing Tiers, Add-ons, and Prerequisites

  • Amazon S3 Multicloud Scanning Connector: Functionality requires purchasing a separate, dedicated add-on SKU on top of the base Microsoft Purview account tier.
  • On-Premises DLP Repository Licensing: DLP enforcement across on-premises file shares requires every user who creates, adds, or consumes files in scanned locations to possess an appropriate Microsoft 365 DLP license (licensing the scanner service account alone is insufficient).
  • Scanner Service Account Licensing: The dedicated Active Directory service account used to run the Information Protection Scanner must be assigned an active Microsoft 365 license containing Information Protection capabilities to execute classification, labeling, and protection tasks.
  • DSPM for AI Copilot Insights Prerequisite: Ingesting and viewing Microsoft 365 Copilot usage analytics and oversharing risks within the DSPM for AI dashboard requires users to be actively licensed for Microsoft 365 Copilot.

7. Explicit Silence, Unverified Features, and Architecture Conflicts

  • Government Air-Gap / Secret Cloud Silence: The authoritative source documentation provides zero operational data regarding feature availability, SKUs, or infrastructure deployment for Azure Government Secret, Azure Government Top Secret, or physically air-gapped classified clouds.
  • FedRAMP Accreditations Conflict: A direct documentation conflict exists between Microsoft official publications:
    • Microsoft 365 Service Descriptions explicitly state that GCC meets FedRAMP Moderate.
    • Azure Security Fundamentals documentation explicitly states that GCC meets FedRAMP High.
    • Architecture Guidance: The true accreditation status must be resolved against the official FedRAMP Marketplace listing prior to finalizing system security plans (SSPs).
  • Third-Party Government Availability: Integration of OneTrust findings into Purview DSPM via Microsoft Sentinel Content Hub is strictly marked as UNVERIFIED for GCC, GCC High, and DoD environments, as no official Microsoft documentation confirms government-cloud availability for this connector.
